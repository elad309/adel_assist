# דמו חי — Invisible Admin (Adel Assistant)

מסמך עזר לפגישה ביום שלישי. תרחיש: **קבלן שיפוצים** עם לקוח שמבקש מידע ופגישה.

## הכנה לפני הפגישה

### 1. הגדרה (חד פעמית)
- [ ] ‏`.env` מלא — כולל `ADEL_ADMIN_TELEGRAM_ID` של הטלפון שלך
- [ ] שתי מיגרציות הוצאו על Supabase
- [ ] `npm run dev` רץ ברקע
- [ ] שלח `/start` לבוט מהחשבון שלך → תיווצר רשומת owner + business

### 2. טעינת מסמך הדגמה
שלח לבוט (כ-owner) הודעה:
```
!doc faq.txt
[הדבק כאן את התוכן של demo/sample-business-faq.txt]
```
או שלח את `demo/sample-business-faq.txt` כקובץ צמוד.

ייקח כ-15-30 שניות (תלוי בכמות chunks). הבוט יענה: "קלטתי את 'faq.txt' — N קטעים".

### 3. הקמת לקוח דמה
- פתח חשבון טלגרם שני (אפשר על מכשיר אחר או חשבון בדיקה)
- שלח `/start` לבוט. הוא ירשם כ-`client`. ה-owner יקבל ping: "לקוח חדש פנה: [שם] (id=N)"
- מהחשבון של ה-owner: `/claim N client`

### 4. פתח טאבים בדפדפן לפני הפגישה
- Supabase SQL Editor
- 3 שאילתות מוכנות (להעתקה למטה)

## רצף הדמו (4-5 דקות)

### שלב 1 — תפיסת הרעיון (30 שניות, מילולי)

> *"בעלי עסקים קטנים — שיפוצניקים, בעלי מספרה, מתקיני מזגנים — מבזבזים שעות ביום על וואטסאפ. עונים שוב ושוב על אותן שאלות. בניתי עוזרת AI שיושבת על הטלגרם של העסק [WhatsApp בהמשך], עונה אוטומטית כשהיא יודעת, ומבקשת אישור כשהיא לא. אני אראה לכם בדיוק איך זה נראה."*

### שלב 2 — לקוח שואל שאלה שיש עליה תשובה במסמכים (RAG grounded)

מהחשבון של הלקוח, שלח לבוט:
> "מה ההבדל בין HPL לאקרילי?"

**מה יקרה:**
- הלקוח יקבל תוך 2-3 שניות תשובה מבוססת על המסמך
- אצלך, בקונסול, תראה לוג: `[u2/client] [rag_grounded] 1240ms`
- ב-DB ל-`adel_execution_log` תיכנס שורה עם `route='rag_grounded'`

**מה אתה אומר:**
> *"היא לא הזיותית. היא מצטטת ממסמך שאני העלתי. אם המסמך לא יודע — היא לא מדמיינת."*

### שלב 3 — לקוח שואל משהו שאין במסמך (Draft & Approve)

מהחשבון של הלקוח, שלח:
> "אפשר לקבוע פגישה ביום ראשון?"

**מה יקרה:**
1. הלקוח מקבל מיד: *"אני בודקת מול הצוות ואחזור אליך בהקדם."*
2. אצלך (owner) קופץ ping:
   ```
   📩 לקוח (X) שאל:
   "אפשר לקבוע פגישה ביום ראשון?"

   הצעת תשובה:
   "אבדוק את הזמינות של בעל העסק ואחזור אליך תוך שעה."
   ```
   עם 2 כפתורים: ✅ אשר ושלח / ❌ דחה

3. אתה לוחץ ✅ — הלקוח **עכשיו** מקבל את ההודעה

**מה אתה אומר:**
> *"זה הלב של המוצר. הבעלים אף פעם לא חותם על משהו שהוא לא ראה. הלקוח מקבל מענה אנושי, מהיר, אבל לא יכול ללכת לאיבוד תחת התחייבות שגויה. זה מה שהופך את זה ל-deployable היום, לא ל-prototype."*

### שלב 4 — Owner שואל את הבוט שאלות פנימיות

מהחשבון שלך:
> "מה הלו"ז שלי השבוע?"

**מה יקרה:** הבוט מציג את 3 האירועים ב-stub calendar.

> "תזכרי שמפתחות הסטנדרטיים נמצאים בקופסה הירוקה במשרד"

**מה יקרה:** סקריפט `memory.remember` שמר ב-CausaDB.

> "איפה המפתחות?"

**מה יקרה:** סקריפט `memory.recall` החזיר את התשובה תוך < 100ms (לא דרך LLM).

**מה אתה אומר:**
> *"שני הדברים האחרונים לא נגעו ב-LLM בכלל. סקריפטים דטרמיניסטיים. ככל שהמערכת לומדת איזה שאלות חוזרות, היא הופכת לפחות תלויה ב-LLM, לא יותר. זה הופך את זה לכלכלי בסקייל."*

### שלב 5 — מסך השליטה (פתח Supabase)

הרץ את 3 השאילתות, אחת אחרי השנייה:

#### א. כל ההודעות הציבוריות עם הroute שלהן
```sql
select id, route, handler, latency_ms, query, response, created_at
from adel_execution_log
order by created_at desc
limit 10;
```
**מה אתה מצביע:** *"רואים? הראשונה rag_grounded — 1.2 שניות. השנייה draft_for_owner. השלישית script — 90 מילישניות. כל אחת מתועדת. אני יודע איפה הבוט עובד טוב ואיפה הוא נכשל."*

#### ב. תור הטיוטות (HitL)
```sql
select id, status, client_query, drafted_reply, approved_at, sent_at
from adel_drafts
order by created_at desc;
```
**מה אתה מצביע:** *"זה התור. כל מקרה שהבוט לא היה בטוח — מתועד. הבעלים רואה בדיוק מה הוא אישר ומתי."*

#### ג. מקורות שה-RAG השתמש בהם
```sql
select route, intent, response, created_at
from adel_execution_log
where route = 'rag_grounded'
order by created_at desc;
```
**מה אתה מצביע:** *"כל תשובה שלי מצוטה — ה-`intent` כולל את שמות הקבצים שהמודל הסתמך עליהם. אם הלקוח ישאל את הבעלים 'איך הבוט יודע X' — יש תשובה."*

### שלב 6 — סגירת הסיפור (1 דקה)

> *"מה שראיתם זה MVP מלא, רץ. אבל הוא לא בכוונה מקיף — בכוונה צמצמנו ל-3 דברים: עונה ללקוחות, מבקש אישור כשלא בטוח, מנהל לוח זמנים פנימי. ה-WhatsApp הוא adapter. PDF זה עוד 30 שורות קוד. Voice — Whisper. הליבה — Role routing + HitL + RAG מצוטה — מוכנה. הצעד הבא הוא לא לבנות עוד פיצ'רים. זה למצוא את הקבלן הראשון שמשלם 99 ש"ח, להעלות אותו, ולמדוד כמה שאלות נענות אוטומטית מול כמה דורשות אישור. ככל שזה ילך טוב — היחס יעלה, המחיר יישאר זהה, השוליים יגדלו."*

## תרחישי כשל אפשריים בדמו (היה מוכן)

| תרחיש | מה לעשות |
|---|---|
| Telegram bot לא מגיב | תבדוק ש-`npm run dev` רץ. תבדוק שאין הודעת שגיאה. |
| RAG לא מחזיר grounded | הסף 0.55. אם השאלה מנוסחת רחוק מהמסמך — יידחה ל-draft. תכין שאלה ש**בטוח** קרובה ("HPL", "מחיר מטבח") |
| Embeddings איטיים בהעלאה | לא נורא, זה קורה לפני הפגישה. אם זה קורה תוך כדי — דבר על המסך עד שיגמר |
| Approve button לא עובד | תבדוק שה-owner_telegram_id ב-DB מצביע על המספר הנכון |
| מישהו שואל "למה לא וואטסאפ?" | *"WhatsApp Business API דורש 4-6 שבועות לאישור Meta. בניתי על Telegram כי הליבה זהה — adapter swap. ברגע שיש לקוח משלם, אתחיל את תהליך האישור במקביל."* |

## SQL מוכנים להעתקה

```sql
-- א. רצף הודעות + routes
select id, route, handler, latency_ms,
       left(query, 60) as query,
       left(response, 80) as response,
       created_at
from adel_execution_log
order by created_at desc
limit 15;

-- ב. תור drafts (HitL queue)
select id, status,
       left(client_query, 50) as client_q,
       left(drafted_reply, 60) as drafted,
       approved_at, sent_at
from adel_drafts
order by created_at desc;

-- ג. סטטיסטיקות routing
select route, count(*), round(avg(latency_ms)) as avg_ms
from adel_execution_log
group by route
order by count(*) desc;

-- ד. document chunks pro business
select d.filename, count(c.id) as chunks
from adel_documents d
left join adel_document_chunks c on c.document_id = d.id
group by d.id, d.filename;
```
